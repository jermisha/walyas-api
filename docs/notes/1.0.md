## Question 3: Multi-Tenant Data Isolation
Imagine our platform has 10,000 users. User A owns portfolio P100, and User B owns portfolio P200. An authenticated request arrives:
GET /api/v1/portfolios/P200
Authorization: Bearer <user-A-token>

The portfolio exists in PostgreSQL, but belongs to User B.
What is the best backend design?

`Ans`: 
Authenticate User A and query PostgreSQL using both the portfolio ID and the authenticated user's ID, returning 404 Not Found when no authorized portfolio matches.

`Details`:
This is a fundamental security principle for our multi-user trading platform: authentication identifies the user; authorization determines which resources that user can access.
Suppose PostgreSQL contains:

| Portfolio ID | Owner | Name |
|--------|--------|--------|
| P100 | User A | Long-Term Investing |
| P200 | User B | Algorithmic Trading |
| P300 | User A | Retirement |
When User A requests P200, the backend must prevent access, even though the portfolio exists.
A safe SQL query is:

SELECT id, user_id, name
FROM portfolios
WHERE id = $1
  AND user_id = $2;

Here, $1 is the requested portfolio ID and $2 is the authenticated user's ID, obtained from validated authentication credentials—not from an untrusted request parameter.
If no row matches, return 404 Not Found. This also avoids revealing whether another user's portfolio exists.
How we'll implement this in Go

type PortfolioRepository interface {
    GetByIDForUser(
        ctx context.Context,
        portfolioID string,
        userID string,
    ) (Portfolio, error)
}
The repository enforces ownership when retrieving the portfolio. Later, we'll add PostgreSQL Row-Level Security as defense in depth.

# Question 5: Domain Modeling in Go
Let's implement our first real domain entity: Portfolio.

Which approach best protects portfolio business rules?
`Ans`: 
Keep important fields unexported, create a constructor that validates required values, and expose methods for permitted state changes.

For The Walyas Project, we want portfolios to maintain valid state regardless of whether changes originate from an HTTP API, a trading strategy, or a future distributed service.

Consider this model:
type Portfolio struct {
    id     string
    userID string
    name   string
}
The fields are unexported, so other Go packages cannot modify them directly.
We can provide a constructor:

func NewPortfolio(
    id, userID, name string,
) (*Portfolio, error) {
    if id == "" || userID == "" || name == "" {
        return nil, errors.New("missing required fields")
    }

    return &Portfolio{
        id:     id,
        userID: userID,
        name:   name,
    }, nil
}

Now every portfolio created through NewPortfolio must satisfy our initial validation rules. We should also avoid exposing alternative construction paths that bypass these invariants.
For example, changing a portfolio's owner should not be a casual field assignment.

Create your first domain file
Create internal/portfolio/portfolio.go:

package portfolio

import (
    "errors"
    "strings"
)

type Portfolio struct {
    id     string
    userID string
    name   string
}

func New(id, userID, name string) (*Portfolio, error) {
    if strings.TrimSpace(id) == "" ||
        strings.TrimSpace(userID) == "" ||
        strings.TrimSpace(name) == "" {
        return nil, errors.New("invalid portfolio")
    }

    return &Portfolio{
        id:     id,
        userID: userID,
        name:   name,
    }, nil
}

func (p *Portfolio) ID() string {
    return p.id
}

func (p *Portfolio) UserID() string {
    return p.userID
}

func (p *Portfolio) Name() string {
    return p.name
}

func (p *Portfolio) Rename(name string) error {
    if strings.TrimSpace(name) == "" {
        return errors.New("portfolio name cannot be empty")
    }

    p.name = name
    return nil
}

This is our first domain entity. Later we'll add investment profiles, portfolio positions, and persistence.

New() vs NewPortfolio()
Imagine our portfolio package eventually contains several domain entities:
type Portfolio struct{}
type Position struct{}
type Allocation struct{}

Then explicit constructors can make sense:
portfolio.NewPortfolio(...)
portfolio.NewPosition(...)
portfolio.NewAllocation(...)
or 
portfolio.New(...)          // Main Portfolio entity
portfolio.NewPosition(...)
portfolio.NewAllocation(...)

As the domain grows, we can introduce more descriptive constructors where they improve clarity.
One important Go detail: New is not a special keyword. Go has no constructor syntax for structs. New is simply a conventional function name.

Next, we want to save portfolios in PostgreSQL.

`Details`:
 
# Hexagonal Architecture (Ports and Adapters). (Repository pattern)
The key principle is:
Our portfolio domain defines what persistence operations it needs. PostgreSQL provides an implementation without controlling the domain model.
1. Repository architecture
Portfolio Application Service
Create · Rename · Retrieve portfolios
Portfolio Repository Interface
Defines persistence operations

Tests and early development

Implement the repository interface
Create:
internal/portfolio/repository.go

package portfolio

import (
    "context"
    "errors"
)

var ErrNotFound = errors.New("portfolio not found")

type Repository interface {
    Save(ctx context.Context, p *Portfolio) error

    GetByIDForUser(
        ctx context.Context,
        portfolioID string,
        userID string,
    ) (*Portfolio, error)
}

Notice three design decisions:
- context.Context supports cancellation and deadlines.
- Save abstracts persistence without exposing SQL.
- GetByIDForUser explicitly scopes retrieval to the authenticated user.
The repository interface belongs to the portfolio module. Later, a PostgreSQL adapter will implement it.

## Question 9: Concurrency Safety

Our HTTP server processes multiple requests concurrently.
Two goroutines call Save() at the same time.
What is the biggest problem with this implementation?

`Ans`: Concurrent writes to a regular Go map are unsafe and can cause data races or runtime failures. We should protect access using sync.RWMutex or another concurrency-safe design

`Details`
Concurrent writes to a regular Go map are unsafe. They can produce data races and runtime failures.
For The Walyas Project, we'll protect our in-memory repository using sync.RWMutex.

Why RWMutex?
Method	Lock	Reason
Save()	Lock()	Exclusive access while modifying the map
GetByIDForUser()	RLock()	Multiple readers can access the map concurrently

One important limitation: the mutex protects the map, but not the mutable Portfolio objects referenced by its pointers. If a caller invokes Rename() concurrently, a data race can still occur.
